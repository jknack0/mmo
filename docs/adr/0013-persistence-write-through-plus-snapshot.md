# Persistence: write-through for high-value events, 30s snapshot for session state

A two-tier persistence model. **High-value events** (item drops, trades, vendor purchases, level-ups, passive point allocation, quest-completing kills) commit synchronously to Postgres — the player's confirmation message fires only after the DB write succeeds. **Session state** (position, current HP, equipped loadout, active discipline) is snapshotted to Postgres every 30 seconds and on every zone change and clean logout. On crash, players are rolled back to their last snapshot and kicked to character select. **Transient combat state** (mob HP, buffs, cooldowns, projectiles, world-boss state) is in-memory only — if a channel crashes mid-fight, the encounter is gone but the characters survive. World bosses reschedule on restart.

**Trades use Postgres transactions, strictly.** Two-phase commit pattern: lock both inventories, validate, atomic swap, unlock — all in one SQL transaction. **No code path ever does "delete from A, then insert into B" without a transaction.** Item IDs are server-generated UUIDs that the client never authors; an item exists if and only if there is a Postgres row for it. Every trade, every drop above a value threshold, and every account-level action writes to an immutable audit log table.

**Storage topology**: a single Postgres for v1 (sharding is a self-inflicted wound at this scale; vertical scaling on a $50/mo VPS handles 1k–2.5k concurrent with massive headroom). Redis for sessions, channel-routing, rate limits, pub/sub, and live chat (last 200 messages per zone, 24h TTL); a rolling job archives older chat to Postgres. **Backups**: daily snapshots plus continuous WAL archiving to object storage for point-in-time recovery. This is the single non-negotiable infra item — backup cost is trivial, the catastrophe-prevention value is total. A corruption event without backups kills the game permanently.

The deliberate departures: nothing is sharded; nothing is eventually-consistent; no NoSQL. The boring choice is the right choice at this scale, and the dupe-prevention trifecta (transactional trades + server-issued UUIDs + audit log) requires the relational guarantees that only Postgres-class systems provide cheaply.
