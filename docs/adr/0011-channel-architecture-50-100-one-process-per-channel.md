# Channel architecture: 50 per open-world zone, 100 per town, one OS process per channel

Open-world zone channels cap at 50 concurrent players; town channels cap at 100; scheduled world-boss instances also cap at 100. Each channel is its own dedicated OS process owning all entities in that channel, with stateless horizontal scale-out (when channel 1 hits 45/50 it stops accepting joins, channel 2 spawns). The cap of 50 is the sweet spot where a Node.js process can comfortably handle full state replication at 10–20 Hz without needing area-of-interest filtering — above ~100 per channel that becomes mandatory, which is a discrete jump in engineering complexity not worth taking for the v1 player-density goal. Towns get the higher cap because they have no combat (no mobs, no projectiles), so the CPU/network budget is mostly free for player presence. The per-channel single-process model is chosen over multi-channel-per-process multiplexing because it gives crash isolation (one channel down doesn't take others) and a clean mental model — the multiplexing alternative saves machines but adds complexity that a solo dev cannot pay for. Targeted total concurrent player budget for v1 is 1,000–2,500, achievable on modest cloud infrastructure (~$300–$500/month). This implicitly constrains the server runtime to something Node-class or better; Rust/Go could push per-channel caps to 200+ if we wanted, which is the natural lever to pull if scale demands it.
